Agents

Three agents I built and measured

A UX reviewer, a QA engineer and a staff PM. Each has a written job, a run log and an eval against a plain Claude session. This page shows what the runs support and where they don’t.

In two minutes

Problem
Claude Code is only as good as the process around it. I was running it across several products faster than I could review, and I could not tell which prompts actually helped.
My call
Give each role a written job, a done test and a stop rule, then score it against a plain Claude session where I have a comparison. Claim only what the run logs show, including where the agent is no better.
Result
Logged runs for all three, held-out scores for QA-TDD and Staff PM, and one demo run for UX (5 to 7 of 10). QA-TDD is far more dependable on its report contract but finds about as many bugs as plain Claude. Staff PM’s lift is small and not consistent.

What I haven’t proven ↓

UX agent

Reviews, files, rechecks

Reviews a live product screen by screen, files the problems and checks again after the fix.

It captures flows with Playwright, reviews against written rules (WCAG, clean UI, dark mode), files GitHub issues for P0 and P1 findings, then re-shoots and reports what is fixed, reopened or still open.

5 → 7 of 10A small demo app, before and after one fix PR. The bar is 8.
8 of 11findings gone after the recheck. 3 wording findings stay open.

First full loop: 36 screenshots in 15 seconds, local and free. The 5 to 7 score is one product and one run, graded on the agent’s own rubric.

QA-TDD

Test first, honest verdict

Writes the failing test first, runs every suite and never reports green on a flaky run.

It owns the tests before and after a build, writes a fixed report with priorities and finding IDs, and cannot edit source. 11 runs are logged.

Plain Claude finds almost as many defects. The agent’s lift is the contract: a failing test first, a flaky-not-green verdict and a fixed report. It does not find more bugs than a plain session, and I don’t claim it does.

Staff PM

Lazy prompt to real spec

Turns a lazy prompt into a spec with testable criteria and catches what the ask leaves out.

It reads the real repo state, writes acceptance criteria and cuts scope. The test is whether the spec covers the missed criterion with something testable.

In progress

Built, not yet measured

  • Stakeholder agent. Simulated readers (recruiter, hiring manager, staff engineer) guess where they would stop on a page, and a checker rejects any finding whose quote is not in the source text. Packaged as a plugin. No eval yet, and its findings are hypotheses to check with real people.
  • Pipeline runner. A ledger with stop rules that chains spec, tests, build and review. Built with tests. No end-to-end run scored yet.

Limits

What I haven’t proven

  • The cases are mine, built from real misses in my own products, and most were run once per arm.
  • Graders are Claude Opus models, blind to which arm wrote the answer.
  • Dev scores are not claims. Only held-out sets are in the tables.
  • Cost per run and accepted-finding rate are not measured.
  • The UX gain is one demo and one run. The pipeline runner and stakeholder agent have no scored run yet.

The agents, eval cases, run logs and scorecard tool are in the studio-agents repo. Running node tools/agent-scorecard.mjs regenerates every number above.
